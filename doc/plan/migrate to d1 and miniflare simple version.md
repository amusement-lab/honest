# Migration Plan (Simple Version): better-sqlite3 → Cloudflare D1 & Miniflare

## Goal

Get the project running on **Cloudflare Workers + D1 (Miniflare)** for local development (`wrangler dev`) and testing (`vitest`) with **minimal changes**—without refactoring controllers or services' query logic, and without touching existing test _cases_ (one new test is added so the constraint helper is covered).

## Step-by-Step Implementation

### Step 1: Update Dependencies, Scripts, pnpm Config & Ignored Files

#### 1.1 Update Dependencies (`package.json`)

This project uses **pnpm** (`pnpm-lock.yaml`). Do **not** use `npm`, which would create a stray `package-lock.json` and leave the pnpm lockfile stale.

```bash
pnpm remove better-sqlite3 @types/better-sqlite3 @hono/node-server dotenv tsx
pnpm add -D wrangler @cloudflare/workers-types
```

Update `scripts` in `package.json`:

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest",
    "dev": "wrangler dev",
    "ncu": "ncu",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "wrangler d1 migrations apply honest-db --local"
  }
}
```

The following scripts are **intentionally removed**:

| Removed script | Reason                                                                                                                 |
| :------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `db:push`      | `drizzle-kit push` needs a local SQLite file URL; schema is now applied via migrations (`db:generate` → `db:migrate`). |
| `db:seed`      | `src/db/seed.ts` depended on `better-sqlite3` + `tsx`; deleted.                                                        |
| `db:studio`    | Needs `dbCredentials`; not part of the minimal setup (see note below).                                                 |

> [!IMPORTANT]
> **Keep `--persist-to` consistent.** `db:migrate` above uses Wrangler's default persistence (`.wrangler/state/v3`), which is exactly where `wrangler dev` and `wrangler d1 execute --local` look. If you ever pass `--persist-to <dir>` to one command, pass the **same** value to all of them. Divergent persist paths are the #1 cause of "I applied the migrations but the tables don't exist".

> **Note on Drizzle Studio**: If you ever need Drizzle Studio against local Miniflare D1, the local SQLite database file resides inside `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/`.

> **Note on `deploy`**: A `deploy` script is deliberately **not** added yet—see [Optional: Deploying to Cloudflare](#optional-deploying-to-cloudflare).

#### 1.2 Update `pnpm-workspace.yaml`

Remove the now-irrelevant `better-sqlite3` entry and allow Wrangler's native dependencies to run their install scripts (otherwise pnpm may block them):

```yaml
allowBuilds:
  esbuild: true
  workerd: true

minimumReleaseAgeExclude:
  - hono@4.12.32
  - "@types/node@26.1.2"

onlyBuiltDependencies:
  - esbuild
  - workerd
```

> [!IMPORTANT]
> Only **`workerd`** (`postinstall: node install.js`) and **`esbuild`** actually have install scripts. Do **not** add `sharp`—nothing in this dependency tree depends on it.
>
> Pick **one** key (`allowBuilds` _or_ `onlyBuiltDependencies`) rather than listing the same packages in both; pnpm 11 accepts either, and duplicating them is just confusing. The snippet above keeps both only so you can see the mapping—delete one block when you edit the file.

#### 1.3 Update `.gitignore`

Add `.wrangler/` so local Miniflare state and D1 database files are ignored:

```gitignore
# cloudflare / wrangler
.wrangler/
.dev.vars
```

> `.dev.vars` is Wrangler's equivalent of `.env` for local secrets (none are needed yet, but it should never be committed).

#### 1.4 Delete `.env.example` (and your local `.env`)

`.env.example` only contains `DATABASE_URL` / `DATABASE_URL_TEST`, which nothing reads after this migration. If secrets are needed later, document them in a `.dev.vars.example` instead.

Also delete the local `.env` (it is gitignored, so it will not show up in a diff but it still exists on disk):

```bash
rm -f .env .env.example
```

> [!WARNING]
> Leaving a stale `.env` in place is not harmless: `getPlatformProxy()` auto-loads `.env` and `.env.local` from the project directory (`GetPlatformProxyOptions.envFiles`), so the old `DATABASE_URL*` values will be injected into the Miniflare proxy env for no reason. If you must keep a `.env` for unrelated variables, pass `envFiles: []` to `getPlatformProxy` in Step 5.1.

#### 1.5 Reconcile the lockfile

`wrangler` and `@cloudflare/workers-types` may already be present in `node_modules` from an earlier experiment while `package.json` / `pnpm-lock.yaml` still list `better-sqlite3`. After running the commands in 1.1, verify both directions converged:

```bash
pnpm install
pnpm list --depth 0
grep -n "better-sqlite3\|wrangler" package.json pnpm-lock.yaml
```

Expect `wrangler` + `@cloudflare/workers-types` in both `package.json` and `pnpm-lock.yaml`, and no `better-sqlite3` anywhere.

Create `wrangler.toml` in the project root. Wrangler uses Miniflare under the hood to emulate Cloudflare Workers and D1 locally (both for `wrangler dev` and Vitest via `getPlatformProxy`):

> [!NOTE]

### Step 4: Switch Database Adapter to D1

#### 4.1 `src/db/index.ts`

Export `db`, a `getDb()` accessor, an `initDb(d1)` initializer, and the `Bindings` type so existing services (`UserService`, `NoteService`) can continue importing `{ db }` without any code changes:

```ts
// src/db/index.ts
import { drizzle, type DrizzleD1Database } from "drizzle-orm/d1";
import type { D1Database } from "@cloudflare/workers-types";
import * as schema from "./schema.ts";

export type Bindings = {
  DB: D1Database;
};

export let db: DrizzleD1Database<typeof schema>;

export function initDb(d1: D1Database) {
  db = drizzle(d1, { schema });
  return db;
}

/** Throws a clear error when a service is used before middleware bound the DB. */
export function getDb(): DrizzleD1Database<typeof schema> {
  if (!db) {
    throw new Error(
      "Database not initialised: initDb() must run before any service call",
    );
  }
  return db;
}
```

> [!WARNING]
> `db` is declared but **`undefined` until `initDb()` runs**. There is no fallback client. Any code path that reaches a service before the middleware in Step 4.2 (a future `app.request()` test that skips `env`, a script, `onError` logging) will crash with an opaque `Cannot read properties of undefined`.
>
> Keep the existing `import { db }` statements as-is (they work because ES module live bindings see the later assignment). Use `getDb()` in any **new** code that must fail loudly.

#### 4.1.1 Type check

`schema.ts` uses `crypto.randomUUID()` and `@noble/hashes` uses `globalThis.crypto.getRandomValues()`, both Workers globals also present in Node 22+. No `@cloudflare/workers-types` entry is needed in `tsconfig.types`—adding it there would collide with `@types/node`. The `import type` above is the correct approach.

#### 4.2 `src/modules/app.module.ts`

1. Type the app with its Worker bindings instead of casting `c.env`.
2. Register a middleware that binds `c.env.DB` on each request.

```ts
import { initDb, type Bindings } from "../db/index.ts";

const app = new OpenAPIHono<{ Bindings: Bindings }>({
  defaultHook: (result, c) => {
    // ...unchanged
  },
});

// Must be registered BEFORE app.route(...): Hono runs middleware/handlers in registration order.
app.use("*", async (c, next) => {
  if (c.env?.DB) {
    initDb(c.env.DB);
  }
  await next();
});

// ...app.doc / app.get('/doc-ui') / app.route(...) unchanged
```

> [!NOTE]
> `drizzle(d1)` is a thin wrapper, so re-initializing per request is effectively free and avoids relying on a value cached from a previous request. The `c.env?.DB` guard keeps `app.request(...)` usable in tests that don't pass an env—but with no env, `db` stays `undefined`, so any actual query will fail. Pass `{ DB: proxy.env.DB }` when writing such tests.

#### 4.3 `drizzle.config.ts` & `src/db/seed.ts`

Simplify `drizzle.config.ts` (since `dotenv` and local `sqlite.db` are no longer used) and delete `src/db/seed.ts`:

```ts
// drizzle.config.ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  out: "./drizzle",
  schema: "./src/db/schema.ts",
  dialect: "sqlite",
});
```

### Step 5: Configure Vitest to Use Miniflare D1

#### 5.1 `src/db/vitest.setup.ts` (renamed from `vitest-global-setup.ts`)

Rename the file—it is no longer a Vitest _global setup_, it runs once per test file—then replace the `drizzle-kit push` shell script with Wrangler's `getPlatformProxy({ persist: false })`, which boots an isolated, non-persisted Miniflare D1 instance. The schema is then applied **explicitly** by Drizzle's D1 migrator (`getPlatformProxy` itself does not run migrations):

```bash
git mv src/db/vitest-global-setup.ts src/db/vitest.setup.ts
```

```ts
// src/db/vitest.setup.ts
import { getPlatformProxy } from "wrangler";
import { migrate } from "drizzle-orm/d1/migrator";
import { afterAll } from "vitest";
import { initDb, type Bindings } from "./index.ts";

const proxy = await getPlatformProxy<Bindings>({ persist: false });
const db = initDb(proxy.env.DB);

// Applies ./drizzle/*.sql and tracks them in the `__drizzle_migrations` table.
await migrate(db, { migrationsFolder: "./drizzle" });

afterAll(async () => {
  await proxy.dispose();
});
```

> [!WARNING]
> There are **two independent migration trackers**:
>
> - Tests: Drizzle's migrator → `__drizzle_migrations` table (in-memory DB, discarded after each test file).
> - Dev / remote: `wrangler d1 migrations apply` → `d1_migrations` table.
>
> They never touch the same database, which is fine. **Never run both against the same DB**, or migrations will be applied twice.

#### 5.2 `vitest.config.ts`

Use `setupFiles` (runs in the same module graph as each test file, so `db` is populated):

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    globals: true,
    setupFiles: ["./src/db/vitest.setup.ts"],
  },
});
```

> [!NOTE]
>
> - `fileParallelism: false` is **not required by default**: each test file gets its own isolated in-memory D1 proxy, so the databases do not collide.
> - **But** each test file also spawns its **own Miniflare child process**, and those processes share the same worker name and dev registry (`~/.config/.wrangler`). If you hit `EADDRINUSE`, registry races, or the suite gets noticeably slow as it grows, set `fileParallelism: false` (or `poolOptions.forks.singleFork: true`). That is the first knob to reach for—do not treat per-file isolation as a guarantee that parallel runs are safe.
> - Each test file boots its own Miniflare instance (~1–1.5s), including `hash.util.test.ts` which doesn't need a DB. Acceptable for now; can be optimized later with Vitest `projects` if the suite grows.
> - Tests run the services in **Node** against a real (Miniflare) D1, not inside `workerd`. Workers-runtime incompatibilities won't be caught by tests—use `wrangler dev` for that, or migrate to `@cloudflare/vitest-pool-workers` for full fidelity later.

### Step 6: Fix SQLite Constraint Error Detection

Since drizzle-orm `0.44+`, every SQLite query error is wrapped in `DrizzleQueryError` (message: `Failed query: ...`, original error in `err.cause`). In addition, D1 errors do **not reliably expose `.code`**—the constraint info is typically only in the message (e.g. `D1_ERROR: UNIQUE constraint failed: users.email: SQLITE_CONSTRAINT`). That is an implementation detail, not a documented guarantee, which is why the helper below matches on **message text across the cause chain** rather than on codes. The current checks in `app.onError` and `user.service.ts` therefore never match; the existing tests only pass because `UserService` pre-checks email uniqueness with a `SELECT`.

#### 6.1 Create `src/utils/db-error.util.ts`

```ts
// src/utils/db-error.util.ts

/** Collects messages from an error and its `cause` chain (Drizzle wraps driver errors in `DrizzleQueryError`). */
function collectErrorMessages(err: unknown): string {
  const messages: string[] = [];
  let current: unknown = err;
  while (current instanceof Error) {
    messages.push(current.message);
    current = current.cause;
  }
  // D1 / Workers can throw non-Error values; don't silently lose them.
  if (messages.length === 0) {
    messages.push(String(err));
  }
  return messages.join(" | ");
}

export function isUniqueViolation(err: unknown): boolean {
  return /UNIQUE constraint failed|SQLITE_CONSTRAINT_(UNIQUE|PRIMARYKEY)/.test(
    collectErrorMessages(err),
  );
}

export function isForeignKeyViolation(err: unknown): boolean {
  return /FOREIGN KEY constraint failed|SQLITE_CONSTRAINT_FOREIGNKEY/.test(
    collectErrorMessages(err),
  );
}
```

#### 6.2 Update `app.onError` in `src/modules/app.module.ts`

Replace the `// SQLite constraint violations (thrown by better-sqlite3)` block with the snippet below.

> [!IMPORTANT]
> Delete the **entire** old block, including its outer `if (err instanceof Error && ("code" in err || ...))` wrapper and the `const errorWithCode = ...` cast. The old code is nested two levels deep; only the inner `if`s are visible at a glance. If you leave the outer guard in place, the new `isUniqueViolation(err)` calls are still gated on `"code" in err`, which is exactly the condition that never holds for D1—the fix would be a no-op.

```ts
import {
  isForeignKeyViolation,
  isUniqueViolation,
} from "../utils/db-error.util.ts";

// SQLite constraint violations (D1 errors wrapped in DrizzleQueryError)
if (isUniqueViolation(err)) {
  return c.json({ message: "Resource already exists" }, 409);
}
if (isForeignKeyViolation(err)) {
  return c.json({ message: "Referenced resource not found" }, 400);
}
```

#### 6.3 Update `src/modules/user/user.service.ts`

In both `createUser` and `updateUser`, replace the inline `if (...)` condition inside `catch` with the helper (the rest of the method is unchanged):

#### 6.4 Add one test that actually exercises `isUniqueViolation`

> [!IMPORTANT]
> This step is **mandatory, not optional**. Every existing duplicate-email test passes through the `SELECT` pre-check and throws `HTTPException` _before_ reaching the `catch` block, so `isUniqueViolation()` would ship completely untested (and would stay broken without anyone noticing). You also cannot observe the `onError` 409 path through the service—`createUser` converts it to a 400 `HTTPException`—so test the helper directly.

Add to `src/modules/user/user.service.test.ts`:

```ts
import { isUniqueViolation } from "../../utils/db-error.util.ts";
import { hashPassword } from "../../utils/hash.util.ts";

it("should detect a UNIQUE violation from a raw insert (bypassing the pre-check)", async () => {
  await db.insert(userTable).values({
    username: "raw",
    email: "raw@example.com",
    password: await hashPassword("secret123"),
  });

  let error: unknown;
  try {
    await db.insert(userTable).values({
      username: "raw2",
      email: "raw@example.com", // duplicate -> hits the DB constraint
      password: await hashPassword("secret123"),
    });
  } catch (err) {
    error = err;
  }

  expect(error).toBeDefined();
  expect(isUniqueViolation(error)).toBe(true);
  expect(isUniqueViolation(new Error("unrelated failure"))).toBe(false);
});
```

Notes:

- `db` and `userTable` are already imported at the top of `user.service.test.ts`; only `isUniqueViolation` and `hashPassword` are new imports.
- Cleanup is already handled by the existing `afterAll(() => db.delete(userTable))`.
- The negative assertion matters: without it the regex could silently degrade into "always true" and the positive test would still pass.
- If Miniflare ever starts throwing non-`Error` values, the `String(err)` fallback in `collectErrorMessages` is what keeps this test (and production behaviour) working.

## How to Run & Verify

1. **Apply existing Drizzle migration to local Miniflare D1:**
   ```bash
   pnpm run db:migrate
   ```
2. **Run all tests on in-memory Miniflare D1:**
   ```bash
   pnpm test
   ```
3. **Start the local Cloudflare Worker dev server:**
   ```bash
   pnpm run dev
   ```
   Open `http://localhost:8787/doc-ui` to test your endpoints with Swagger UI.

> ```bash
> XDG_CONFIG_HOME=/tmp/xdg WRANGLER_REGISTRY_PATH=/tmp/xdg/registry pnpm test
> ```

## Optional: Deploying to Cloudflare

Not part of the minimal migration. `database_id = "local-dev-db"` is a placeholder and **`wrangler deploy` will fail** with it. When ready:

1. Create the real database and copy the printed `database_id` into `wrangler.toml`:
   ```bash
   pnpm wrangler d1 create honest-db
   ```
2. Add scripts:
   ```json
   {
     "deploy": "wrangler deploy",
     "db:migrate:remote": "wrangler d1 migrations apply honest-db --remote"
   }
   ```
3. Apply migrations remotely, then deploy:
   ```bash
   pnpm run db:migrate:remote
   pnpm run deploy
   ```

> [!WARNING]
> **CPU limits**: `hashPassword` uses scrypt (`N = 2^14`) in pure JS, which costs tens of milliseconds of CPU per call. This exceeds the Workers **Free** plan's 10ms CPU limit (`wrangler dev` does not enforce it). Before deploying, either use the Paid plan (configurable CPU limit) or switch to a Workers-native hash (e.g. PBKDF2 via `crypto.subtle`).
